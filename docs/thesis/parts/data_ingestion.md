# Data Ingestion and Pre-processing

The primary data source is a single CSV file exported from Tallinn's IoT acoustic monitoring platform, containing approximately three million individual sensor readings collected from 471 devices over the four-month period from September to December 2021. Each row in the file represents a single measurement event and carries the sensor name, the recorded sound pressure level in decibels, a production timestamp with UTC offset, and the geographic coordinates of the sensor. Throughout the project, this file is treated as immutable and read-only. All transformations are performed exclusively on derived data written to the database, ensuring that the original export can be re-processed from scratch at any point without risk of data corruption or inconsistency. This design principle supports full reproducibility: given the same source file, the entire pipeline can be re-executed deterministically to produce an identical database.

The ingestion stage is implemented through a sequence of three dedicated Python scripts, each with a clearly scoped responsibility. Rather than loading the full dataset into memory at once, each script processes the CSV in a single streaming pass, which keeps memory usage bounded regardless of file size and allows the pipeline to be run on modest hardware without specialised infrastructure.

The first script, `csv_to_sql.py`, is responsible for constructing the device registry. It streams through the raw CSV and identifies all unique sensor names, recording the first-seen geographic coordinates for each as the canonical device location. Because the raw dataset contains millions of rows with repeated entries per sensor — one row per reading rather than one row per device — this deduplication step is necessary before any downstream processing can reference sensors by a stable identifier. Devices are assigned sequential integer identifiers sorted alphabetically by name, which ensures that identifier assignments remain consistent across multiple runs of the pipeline. The resulting `devices` table forms the authoritative reference for all subsequent tables: every reading, imputed value, and evaluation result is linked back to a device by this identifier. A small number of devices in the raw data exhibit minor variations in reported coordinates across different readings, attributable to GPS noise or metadata inconsistencies in the sensor platform. Since all sensors are fixed physical installations, the first-seen coordinates are retained and any subsequent deviations beyond a tolerance of 1×10⁻⁵ degrees — approximately one metre at Tallinn's latitude — are flagged rather than overwriting the reference location.

The second and most computationally intensive script, `csv_to_sp_levels.py`, transforms the raw per-reading data into a structured table of hourly aggregated sound pressure levels. For each valid row in the CSV, the script parses the production timestamp — which appears in two slightly different format variants across the dataset — converts it from UTC to Tallinn local time (Europe/Tallinn), and truncates it to the start of the corresponding hour. This local time representation is important because urban noise patterns are fundamentally tied to human activity schedules: traffic peaks, working hours, and nighttime quiet periods occur at fixed local times regardless of the UTC offset, which shifts by one hour at the autumn daylight saving transition within the study period. All readings sharing the same device and truncated hour are grouped together and reduced to a single representative value. Formally, let R(d, h) denote the set of all raw readings for device d within hour h. The aggregated value is:

    v(d, h) = round( median( R(d, h) ) )

The median is chosen over the mean because SPL sensors in urban environments frequently capture transient events — a vehicle horn, a nearby construction burst, a firmware spike — that are real acoustic events but not representative of the ambient noise level across an entire hour. For a set of readings containing even a single extreme outlier, the mean is displaced in proportion to the outlier's magnitude, whereas the median remains anchored to the central mass of the distribution. Rounding to the nearest integer reflects the practical measurement limitations of low-cost MEMS microphone hardware, which does not provide reliable sub-decibel precision. Each aggregated value is stored alongside both a human-readable local timestamp string and a Unix UTC integer timestamp, the latter used for all indexed range queries and arithmetic operations within the database. An `imputed` flag is set to zero for every row at this stage, marking all entries as original sensor measurements and distinguishing them from values that will be synthesised during the imputation stage.

The third script, `compute_missing_hours.py`, runs after the imputation tables have been generated and serves a diagnostic and metadata function. Rather than re-reading the raw CSV, it operates entirely on the already-processed `sp_levels` table, querying the minimum and maximum Unix timestamps per device — denoted $t_{\min}$ and $t_{\max}$ — to determine each sensor's operational window. The theoretical total number of hourly slots within this window is:

    total_hours(d) = ( t_max(d) − t_min(d) ) / 3600 + 1

The addition of one ensures inclusive counting of both the first and last hour: a device with readings only at hour 0 and hour 1 spans two hours, not one. The number of hours with at least one observed reading, $\text{hours\_with\_data}(d)$, is obtained by counting distinct hourly timestamps in `sp_levels` for that device. Missing hours are then derived as:

    missing_hours(d) = max( 0,  total_hours(d) − hours_with_data(d) )

The max(0, ·) safeguard handles rare edge cases where rounding artefacts in the Unix timestamp arithmetic cause the observed count to marginally exceed the computed total. These three statistics — total hours, hours with data, and missing hours — are written back into the `devices` table as permanent metadata fields. They serve multiple downstream purposes: the visual dashboard uses them to colour-code sensors by data completeness, the test device selection procedure filters on missing rate to ensure evaluation candidates have sufficiently complete histories, and the imputation scripts use the operational window boundaries to determine which hourly slots require reconstruction.

Together, the three scripts produce two foundational database tables — `devices`, containing one record per sensor with its identifier, coordinates, and coverage statistics, and `sp_levels`, containing one record per device-hour pair with the aggregated SPL value — from which all imputation and evaluation steps read. The pipeline design ensures strict separation between the raw source and the derived database: no script modifies the CSV, and each script writes exclusively to its own designated portion of the schema. This modularity means that individual stages can be re-executed independently if parameters change — for example, if the aggregation window or timezone handling is revised — without requiring a full pipeline restart.

The ingestion process reveals a fleet-wide missing rate of approximately 26%, meaning that roughly one in four expected hourly readings is absent from the raw dataset. This level of incompleteness is not uniformly distributed across the fleet: some sensors have near-complete histories with missing rates below one percent, while others — typically sensors deployed late in the study period, decommissioned early, or subject to repeated connectivity failures — are absent for the majority of their expected operational window. This heterogeneity in missingness patterns motivates both the design of the imputation framework, which must handle a wide range of gap structures, and the stratified evaluation methodology, which ensures that test devices represent the full spectrum of data completeness conditions encountered across the fleet.
